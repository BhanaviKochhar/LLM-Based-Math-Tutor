# Controller Stabilization Audit

Independent verification of the controller-integration stabilization work (commit `d097af4`), checked against the actual code in this session rather than trusted from prior reports. Each of the 12 items below was checked by reading the current implementation and, where practical, by reproducing behaviour directly (not just by inspection).

| # | Property to verify | Verified? | Evidence |
|---|---|---|---|
| 1 | Controller state committed only after a successful action | **Yes** | `frontend/app.py::advance_episode` calls `controller.step()` on `copy.copy(state)` (a snapshot), builds a `trial_episode`, and only assigns `episode["state"] = new_state` *after* `_apply_action(...)` returns without raising. `start_episode` follows the same pattern: `chat["episode"] = episode` is assigned only after `_apply_action` succeeds. Confirmed by direct code read and by `frontend/test_app.py::test_generation_failure_rolls_back_state` / `test_start_episode_does_not_commit_on_failure` (mocked, deterministic). |
| 2 | Failed generation does not falsely advance a tutoring episode | **Yes** | Same mechanism as #1. Additionally, `_run_generation` now raises `GenerationFailed` on an *empty* result (no exception, but no text from any provider) rather than returning `""`, so a silent provider outage is caught by the same rollback path as an explicit exception. Verified by `test_empty_generation_treated_as_failure`. |
| 3 | Episode initialization is safe when generation fails | **Yes** | `start_episode` builds `episode` locally and calls `_apply_action(episode, action, active_turns)` before ever touching `chat["episode"]`; on failure, `chat["episode"]` is left exactly as it was (`None` for a fresh chat). Verified by `test_start_episode_does_not_commit_on_failure`. |
| 4 | Wrong attempts are recorded consistently | **Yes, fixed during this review** | Before the fix: only the *terminal* outcome of an episode triggered `record_feedback`, so a wrong attempt that didn't end the episode (e.g. attempt 1 of 2 before a correct attempt 2) was never recorded at all — an undercount. `_record_outcome` now records every `MODE_DIAGNOSE_WRONG` individually, plus the threshold-triggered `MODE_CO_SOLVE`. Verified by `frontend/test_app.py::test_attempt_recording_semantics`. |
| 5 | Give-up, cold reveal, and co-solve have correct feedback semantics | **Yes, fixed during this review** | `MODE_CO_SOLVE` with `outcome == "gave_up"` and `MODE_REVEAL` with `outcome == "shown"` **and** `state.attempts == 0` (a cold reveal — asked to be shown without ever attempting) are both explicitly excluded from `record_feedback` in `_record_outcome`. Only a `MODE_REVEAL` reached after at least one real attempt (`state.attempts >= 1`) is recorded as incorrect. Verified by the same test, five distinct assertions covering each branch. |
| 6 | Trusted answers are not exposed before the controller permits disclosure | **Yes, unchanged property, re-confirmed** | `computed_answer` is only ever passed into prompt construction (`prompt_registry.build_messages`, via `pipeline.generate_turn`) for `MODE_CO_SOLVE`/`MODE_REVEAL` actions (see `pipeline.generate_turn`'s `reveal_modes` set). All other modes (`teach_invite`, `diagnose_wrong`, `hint`, `ack_conceptual`, `redirect`) pass `injected=None`. Confirmed by direct code read; this logic was not changed in the stabilization work and was already correctly scoped. |
| 7 | User-facing error messages distinguish recoverable failures from ambiguous inputs | **Yes, fixed during this review** | Before: both an exception and an "I didn't understand that" case fell through to the same generic `_friendly_reply` fallback, with no logging. After: `submit_turn`'s `except` block returns a distinct message ("Hmm, something went wrong on my end... nothing was recorded, so please try again.") and calls `logger.exception(...)`; a non-exception empty/falsy result still falls back to `_friendly_reply` (used for genuinely ambiguous/conversational input). Verified by reading `submit_turn` and by the live smoke tests in `docs/development_test_log.md` observing the logged traceback output. |
| 8 | Exceptions logged with useful debugging info, without leaking sensitive data | **Partially verified; one deliberate trade-off flagged** | `logger.exception("submit_turn: generation failed for input %r", text)` logs the student's turn text (needed for diagnosability) to the local server console/log only — no network transmission, no credentials, no `.env` contents. This is a deliberate, scoped trade-off (student input is the minimum needed to diagnose a parsing/generation failure) rather than an oversight; flagged explicitly here rather than silently assumed safe. No student-identifying information (name, session ID) is logged, since `STUDENT_ID` is the fixed string `"session_user"` for all users in the current MVP. |
| 9 | Public wrappers used appropriately instead of private-helper coupling | **Yes** | `frontend/app.py` no longer calls `pipeline._resolve_question`, `pipeline._solve`, `pipeline._make_source`, or `verifier._safe_eval` directly. New public wrappers (`pipeline.resolve_conversation`, `pipeline.compute_trusted_answer`, `pipeline.source_citation`, `verifier.parse_trusted_value`) are thin pass-throughs — confirmed by reading both the wrapper bodies (single-line delegation, no added logic or LLM calls) and by a grep across `frontend/app.py` confirming zero remaining `pipeline\._` / `verifier\._` references. Verified structurally by `frontend/test_app.py::test_public_api_wrappers`, which also asserts the forwarding behaviour by monkeypatching the private functions and checking the call arguments reach them unchanged. |
| 10 | Controller/pipeline/verifier/frontend interfaces are consistent | **Yes, with one documented pre-existing gap** | `frontend/app.py` now calls `pipeline.generate_turn(state, action, ...)` — the bridge that already existed in `pipeline.py` but was previously unused by any live caller. One interface inconsistency found and documented (not fixed, out of scope): `pipeline.generate_turn`'s `thread_notes` parameter (cross-episode memory) is never populated by `frontend/app.py` — same gap that existed in the pre-stabilization code, not newly introduced. |
| 11 | New-question and topic-switch behaviours work as intended | **Yes** | `advance_episode` closes the current episode and calls `start_episode` with the new text whenever intent resolves to `NEW_QUESTION`, whether mid-episode or after a terminal episode. Verified live: `docs/development_test_log.md` scenario 5 confirms `state.question` updates to the new text and the old episode is discarded. |
| 12 | Tracker updated only when the corresponding action is valid | **Yes, this is the same fix as #4/#5** | `_record_outcome` is the single point where `record_feedback` is called, gated on `action.mode`/`action.outcome`/`state.attempts` as described above — not on any separate frontend heuristic. |

## Additional defects found during this audit (beyond the original 12-point checklist)

- **`scripts/llm/test_pipeline.py`'s `"hint level-2 guidance present"` assertion was checking the wrong guidance tier's wording** (fixed in this stabilization round — see `docs/development_test_log.md` for the full root-cause trace). Confirmed pre-existing (neither `hints.py` nor the test file were touched by the controller-integration commit) and not a stabilization regression.
- **`response_parser.final_number_str`'s fallback defect** (Section 5 of this review) — root-caused, fixed, and regression-tested; see `docs/extraction_evaluation.md`.
- **New test function was initially written but not wired into `test_pipeline.py::main()`**, which silently meant the new regression tests never ran despite the suite reporting "0 failed." Caught by explicitly checking `grep -n "def main" scripts/llm/test_pipeline.py` and confirming the new function name appeared in the call list before trusting the pass count — a reminder that "all green" does not by itself prove new tests executed; they must be independently confirmed to have run. Fixed immediately (one-line addition to `main()`).

## Not changed in this pass (explicitly out of scope, not overlooked)

- The conceptual-episode non-progression property (`ctl-012`) — confirmed still present, not newly fixed, per the explicit instruction not to force numeric diagnosis onto non-computable questions without a separate design discussion.
- Retrieval quality for short/bare-topic queries — confirmed still present (see `docs/retrieval_evaluation.md`).
- `thread_notes` memory wiring — pre-existing gap, not touched.
- Enter-to-submit in the Streamlit ask-bar — pre-existing, not a regression, not touched.
- `STUDENT_ID = "session_user"` — pre-existing single-user MVP identity, not touched (see `docs` for the persistence/privacy review).
