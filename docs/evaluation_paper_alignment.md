# Research Paper ↔ Implementation Alignment

## Important caveat on sourcing

**Neither the paper draft (`.tex`/`.pdf`) nor a `.bib` file exists anywhere in this repository** — confirmed by direct inspection of the repository tree during this review, not assumed. The mapping below is therefore built from the paper's `.tex` source as it was shown earlier in this engagement (titled "Tiny Thinker: A Retrieval-Grounded, Verifier-Gated LLM Tutor for NCERT Primary Mathematics"), **not** from a file this repository tracks. If that source has since changed, this document is stale with respect to the paper and should be re-derived from the current paper file, not trusted as-is. The repository and its test/evaluation evidence remain the source of truth for *implementation and measured-performance* claims; this document only maps that evidence against what the paper (as last seen) asserts.

Status categories used below: **Implemented** / **Implemented and tested** / **Experimentally evaluated** / **Partially implemented** / **Not yet evaluated** / **Proposed future work**.

## 1. Objectives and research questions

| Paper item | Status | Evidence / gap |
|---|---|---|
| O1 — reduce hallucinated content via external verifier before answers reach the learner | **Partially implemented** | `scripts/llm/verifier.py` (`solve`/`check`) exists and is now (per the controller-integration checkpoint) actually called on the **live** path for `REVEAL`/`CO_SOLVE` turns via `frontend/app.py::_post_check`, with real post-check results observed in `docs/development_test_log.md`. But: (a) `response_parser.final_number_str`'s fallback-on-no-"Answer:"-line defect means the stated-answer half of the check can itself be wrong (`eval/datasets/extraction/v1_starter.jsonl` ex-009/ex-010, 2/7 measured failures), and (b) the verifier cannot grade conceptual/equivalent-form answers (`co-001`), so O1 is not yet uniformly achieved across question types. |
| O2 — rule-based personalization adjusting explanation style/support intensity | **Implemented and tested** | `scripts/llm/student_tracker.py` (recent-window classification) + `scripts/llm/controller.py` (level-tuned `_COSOLVE_AFTER` thresholds) + `scripts/llm/prompt_registry.py` (`LEVEL_STYLE` blocks). Controller transitions are deterministically tested (`eval/controller_walk.py`, 27/27). Attempt-recording semantics were a genuine defect found and fixed in this checkpoint (see `docs/development_test_log.md` finding C) — before the fix, giving up or a cold reveal could be miscounted as a wrong attempt, which would have fed O2's adaptation loop false signal. |
| O3 — assess system vs. baseline (no verification/personalization) on incorrect answers and hallucinated feedback | **Partially implemented, preliminary evidence only** | `eval/run_eval.py` + `eval/eval_set.py` (36 questions) is real, existing evidence: baseline 35/36 (97.2%), system 36/36 (100%) — this matches the paper's abstract exactly. This is explicitly a **preliminary** comparison (per the project's own planning documents) on arithmetic correctness only; it does not cover hallucinated *feedback* (as opposed to wrong final answers), nor conceptual questions, nor the ablations the paper's own evaluation-strategy section describes as planned. |
| RQ1 — does grade-filtered hybrid retrieval surface curriculum-grounded resources deeply enough? | **Not yet evaluated at scale; new diagnostic evidence surfaces a concrete limitation** | `eval/datasets/retrieval/v1_starter.jsonl` (10 queries, 8 scorable) found Recall@3 = 5/8 on a small, non-representative, specificity-stratified sample — with misses concentrated in short/bare-topic queries (`rq-001` "fractions", `rq-002` "what is a fraction") and hits in longer, specific phrasings of the identical topic (`rq-003`, `rq-004`). This directly informs RQ1 but is explicitly **not** the ≥50-query stratified benchmark the question deserves (see `docs/evaluation_plan.md` §2.3 for the exact caveat). |
| RQ2 — how much does compute-first verification cut false numerical claims, and on what fraction of questions can it operate? | **Not yet evaluated** | The 36-question preliminary set gives one data point (0% wrong vs. 2.8% wrong). "What fraction of questions can it operate at all" (verifier coverage) has no dedicated measurement yet — flagged as `Planned` in the paper's own Table of evaluation metrics, and still planned here; `eval/datasets/arithmetic/v1_starter.jsonl`'s `verifiable: false` cases (ar-005, ar-012, ar-015) are a first step toward measuring coverage but are not yet run as a coverage metric. |
| RQ3 — are learner-level attempt thresholds appropriate (teacher-judged) vs. a fixed policy? | **Not yet evaluated** | No teacher-rating protocol has been executed. `docs/evaluation_plan.md` §3's rubric is a prerequisite for this but has not itself been validated with raters yet. |

## 4. Evaluation-strategy and preliminary-results sections

**Note on the paper's own internal state (as last seen):** the "Preliminary Results" section of the `.tex` source was entirely wrapped in LaTeX comments (`%`) — meaning, as last seen, it was not part of the *compiled/rendered* paper, while the **abstract** states specific figures from that commented-out section (266 sessions, 95% retrieval hit rate, over-refusal 30%→0%, format compliance 15%→65%, 0% hallucination) as if they were presented findings. This is an internal consistency point worth the paper authors' attention — the abstract currently asserts results whose supporting section is not visible in the compiled document — but it is **not this review's place to alter paper text**; it is reported here as a discrepancy for the authors to resolve, per this task's explicit instruction not to rewrite approved objectives or claims.

| Paper's own metric table status | This checkpoint's status |
|---|---|

## 5. Claims that must continue to wait for evidence

Per the paper's own §"Claims That Must Wait for Evidence" and this project's explicit ground rules: improved learning outcomes, superiority over teachers, statistically significant learning gains, a 200-question evaluation, unmeasured retrieval metrics, Cohen's κ, Wilcoxon/McNemar results, user studies, and production-scale reliability remain **unmeasured** after this checkpoint. Nothing in this checkpoint's work constitutes evidence for any of these. This checkpoint's contribution is entirely at the level of: (a) fixing two real discrepancies between the paper's architecture description and the live app (controller integration, live post-check), (b) building the dataset/protocol infrastructure the paper's planned evaluations will need, and (c) surfacing and quantifying a small number of concrete, previously-undocumented gaps (response-parser fallback defect, equivalent-fraction handling, short-query retrieval weakness, conceptual-episode non-progression).
